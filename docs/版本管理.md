# 小日和版本矿坑

本机项目目录中的 Git 仓库负责保存代码、界面、测试、模型运行资源和思考档位配置的历史。更新日志在根目录 `CHANGELOG.md`，当前版本号在 `VERSION`。

## 以后怎么提更新

直接说：“给小日和加……，做完记一版更新日志。”

每次更新依次完成：修改、验证、填写日志、更新版本号、提交代码、建立同名版本标签。未完成实机验证的改动保留 beta 标记。日志可以用小日和施工队的口吻，但只写实际完成的事情。

## 版本号

- `0.1.1`：修 bug 或微调外观。
- `0.2.0`：新增一个可独立描述的小功能。
- `1.0.0`：阶段性稳定发布。
- `0.2.0-beta.1`：尚在验证中的预览版。

不移动旧标签，不重写已发布的提交。需要修订时发布新版本。

## 操作细节

三处版本号要一起改，但**只有 `VERSION` 是程序读的**：

| 位置 | 谁在用 |
|---|---|
| `VERSION` | `src/update.py` 靠它比大小 |
| `README.md` 第 5 行 | 给人看的 |
| `CHANGELOG.md` | 给人看的 |

后两处漏改过：`VERSION` 停在 beta.5 而 README 写着 beta.6，对不上了没人发现。所以程序只认 `VERSION`，别去 README 或日志里抠版本号。

建标签用 `git tag -a`（带注释）。**轻量标签不会被 `git push --follow-tags` 推上去** —— 本地 `git tag` 看得见，远端没有，很容易以为推成功了，下次换台机器拉下来才发现。标签名 = `v` + `VERSION` 的内容。

推送前先 `git status` 看一眼：用户可能在本机改了自己的设置（外观、思考档位），那些是被 `.gitignore` 挡住的，但工作区里的临时改动要分清楚哪些属于这次功能。

## 数据如何保留

密钥、用户档案、人格、聊天与私人记忆仍留在原有本地文件中；`.gitignore` 将它们与代码历史分开。原始资料、旧压缩包、旧备份也保留在磁盘上。运行环境可以重新安装，未纳入代码提交。

所以版本库适合回退代码。需要迁移整套桌宠时，仍要另外打包本地运行资料；恢复代码时不要清理被忽略的文件。

## 查看与回退

可以直接让我“看看最近几版改了什么”或“把上个版本导出一份比较”。默认在另一个目录导出指定版本，先验证再替换，不直接覆盖正在使用的目录。

熟悉 Git 时可用 `git log --oneline --decorate` 查看记录，`git diff` 查看未提交修改，`git tag --list` 查看版本标签。用 `git archive` 导出指定标签中的代码，导出物需要配合现有本地运行资料才能启动。

## 每版日志模板

```markdown
## 0.1.1 · YYYY-MM-DD

**「一句施工队风格的小标题。」**

### 新增 / 修复 / 外观
- 具体改变，以及使用时会有什么不同。

### 验证
- 实际做过的检查；仍待确认的部分写清楚。

### 施工备注
一句轻松的收尾。
```
