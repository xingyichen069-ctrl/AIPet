# 版本与施工日志

Git保存代码、测试、公开默认模板和模型运行资源。当前版本以根目录 `VERSION` 为准，README和CHANGELOG用于阅读。

每次功能或修复完成后：检查差异、验证、更新CHANGELOG、提交代码。没有明确发行请求时不改VERSION、不建标签；未完成必要实机验证时保留beta。没有明确推送请求时只保留本地提交。

## 公开模板与私人文件

`data/config.example.json`、`thinking.example.json`、`secrets.example.json` 是发行模板。程序只在本机对应文件缺失时创建它们；已有 `config.json`、`thinking.json`、`secrets.json` 不被准备程序覆盖，也不再作为发行内容跟踪。

人格、头像、记忆、聊天、密钥、运行环境和历史备份留在本机。Git历史不能替代这些资料的备份。提交前检查差异，不强行加入被忽略的私人文件。

旧版本曾跟踪 `data/thinking.json`，不能将新的保护规则倒推到所有旧压缩包或旧Git检出。普通用户更新按 [README](../README.md#从旧版本更新) 的独立新目录迁移流程，验证后继续保留旧目录；不要靠覆盖或清理被忽略文件更新。

## 发布与回退

明确发版本时一起修改VERSION、README、CHANGELOG。标签按 `v` 加版本号命名，不移动旧标签，不重写已发布提交。仓库共享多个分支的标签，main的发行必须先核对归属，不能只按全仓最大标签判断。

回退默认在另一目录导出旧代码比较，不覆盖当前私人资料。使用Git的维护者可用 `git log`、`git diff` 和 `git archive` 检查、导出；导出的源码仍需准备环境与迁移资料。

## 检查更新的来源

“检查更新”和 `python src/update.py` 默认查询 `xingyichen069-ctrl/AIPet` 的 `main`。先核对该分支当前的提交，再从这个固定提交读取 `VERSION`；源码页面和 ZIP 地址也固定到同一提交。其他分支的标签不参加比较。请求仍使用 `tools.proxy` 配置，只有手动检查时才访问网络。

- 远端版本号更高：提示该分支有较新版本。
- 版本号相同：只确认版本号相同，本次没有比较本机文件，不能据此判断是否漏了后续提交。
- 本机版本号更高：只报告数值关系，不推断来源、兼容性或是否需要降级。
- 本机 VERSION 缺失或无效：仍展示已核对的远端来源，但不推荐升级。
- 分支、版本文件或网络核对失败：报告原因，不回退到其他分支或全仓标签。

fork 或其他分支可在 `data/config.json` 增加以下配置；省略字段时使用默认值：

```json
"update": { "repo": "你的名字/AIPet", "branch": "main" }
```

这只改变检查来源，不改变本机代码。工具不自动下载、覆盖或迁移资料。固定提交也不等于已发行或已验证的稳定版本；下载后仍按独立目录迁移流程检查。旧安装里的检查工具不会因本文更新自动改变行为。

## 日志格式

只写改了什么、为什么改，不加标题语、不编造发布历史。验证方法、实测结果和仍待验证的边界放提交信息或独立审查记录，不放CHANGELOG。

```markdown
## 0.5.0-beta.1 · YYYY-MM-DD

- 补齐首次配置入口，让源码用户能找到密钥填写位置。
- 调整更新说明，使用独立目录迁移并保留旧目录。
```

连续小修可记在同一版或现有“待更新”区；不用为每次提交创建新版本。
